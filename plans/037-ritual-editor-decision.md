# Ritual editor decision — 25 September 2026

**Decision accepted for an app-local pilot:** build the next ritual authoring experience on **Tiptap 3 / ProseMirror**, with a Magickli-owned, versioned semantic document as the saved authority. Keep the existing Pug/shortcut editor and JRT reader for legacy revisions during rollout. The new editor stays app-local until a second product validates extraction. The implementation and remaining release gates are tracked in [the pilot ledger](038-ritual-editor-implementation.md).

**Implementation update:** The pilot now has a tested `magickli-ritual` v1 model, a purpose-built editable ritual text projection with `Sayer: words` and `* Doer action` shortcuts, and a feature-gated v3 SQL writer that stores semantic JSON and compiles JRT profile 1. The proposed schema examples, Markdown/directive grammar and rollout steps below record the original decision process; the pilot ledger and implementation files define what was actually built. The feature flag remains off while browser, mobile, accessibility and broader parity gates are open.

Evidence labels throughout: **Observed** means repository inspection, passing test, or browser run in this trial; **Documented** means the cited upstream contract; **Inferred** means a design judgment not established by the trial; **Failed** means the stated check showed a defect; **Untested** identifies a release gate. All upstream pages and package metadata were accessed on 25 September 2026.

**Observed:** [the SQL write contract](007-sql-ritual-write-contract.md) is already v2. The SQL reader selects only a compatible artifact tied to the current revision; it does not compile on read or pick the newest timestamp. Current source format is `magickli-pug-shortcuts` v1; output is `json-rich-text` profile 1 with a compiler identity. Historical source bytes and artifacts must remain unchanged.

**Observed:** nine existing compiler, JRT, SQL read/write, draft and document editor/reader test files passed (206 tests) in the original checkout on the research date. They protect the current baseline; none tests a production Tiptap integration.

## Proposed document and source authority

Use a **Magickli semantic JSON format v1** as the authority for new WYSIWYG revisions. Tiptap JSON is editor state, **not** the saved contract. The adapter must map semantic JSON ↔ editor JSON and validate on both boundaries. Reasons: editor extensions/schema versions and helper nodes can change; task audiences, declarations, anchors and legacy fallbacks belong to the product contract; reader code should not load editor packages. A small example (the full fixture is in `editor-trial/src/model.js`):

```json
{
  "schemaVersion": 1,
  "roles": ["hierophant", "keryx", "candidate"],
  "aliases": { "hiero": "hierophant" },
  "nodes": [
    { "id": "d2", "type": "declaration", "name": "candidateName", "label": "Candidate name", "input": "text", "default": "Candidate", "options": [] },
    { "id": "t1", "type": "task", "mode": "say", "audience": { "scope": "roles", "roles": ["hiero", "keryx"] }, "children": [
      { "id": "p1", "type": "paragraph", "children": [
        { "type": "text", "text": "Welcome " }, { "type": "variableRef", "name": "candidateName" },
        { "type": "text", "text": " to " }, { "type": "grade", "value": "0=0" }
      ] }
    ] }
  ]
}
```

**Proposed invariants:** each semantic block has a stable UUIDv7 identity; edits/moves keep it; a split or duplication allocates a new UUIDv7 for the new block; inline refs use semantic names, not DOM keys. The trial uses fixed test IDs and browser UUIDv4 only to demonstrate identity behavior. Validate exact node/attribute shapes, task audience scope and known roles/aliases, declaration uniqueness, selectable defaults/options, references to existing declarations, grade syntax, image URL/access and alt text, heading anchor uniqueness, nested shape and size/depth limits. Preserve text Unicode and explicit `lang`/`dir` where needed. Editor selection, history, read-only URL variable values, DOM refs, `forMe`, local draft status and runtime cache keys are transient. Whole-node move must retain ID and semantics; merges across incompatible task audiences must be refused or explicitly confirmed as an audience change. A future normalization pass must be deterministic and idempotent; don't silently invent a different role or discard unknown content.

Unknown semantic node types or unsupported legacy JRT/Pug constructs become **opaque blocks** with their exact original source fragment or original artifact payload plus format/version metadata, a readable fallback label, and an explicit “open legacy source” action. Do not send an opaque block through a lossy editor conversion. If its source span cannot be identified safely, make the entire revision legacy-only until a converter is reviewed. Malformed source remains an unsaved draft with parser diagnostics; the last valid saved revision continues to read. The trial's `mystery-widget` illustrates only the visible placeholder path; it does not prove safe extraction from a production document.

Pug/Jade need not remain the author-facing source format. The first implementation can offer **validated semantic JSON** as an expert source mode, as in the trial, while most authors use WYSIWYG. A future readable export could use Markdown plus explicit directives, for example `:::task mode=say audience=roles(hiero,keryx)` and `{{candidateName}}`, with escaping and a fenced opaque legacy block. That export must be a **derived, versioned projection** until an inverse parser passes round-trips for every supported node. Markdown alone cannot represent nested ritual semantics, role aliases and stable IDs without extensions. Exact Pug whitespace, comments and shortcut spelling are not recoverable from JRT or a semantic edit; historical source bytes remain intact on old revisions.

| Input → output | Rule and status |
| --- | --- |
| Legacy Pug v1 → JRT profile 1 | **Observed existing contract:** compile exact source on create/save; preserve historical artifact and compiler identity. No silent recompile of old revisions. |
| Legacy Pug/JRT → semantic v1 | **Proposed, untested:** one-time opt-in converter with parity report per ritual/construct, original source and artifact retained; unsupported content becomes opaque or blocks WYSIWYG. Never infer semantic IDs from temporary DOM refs. |
| Semantic v1 → Tiptap JSON → semantic v1 | **Observed for synthetic fixture:** adapters and six tests show semantic round-trips and stable repeated conversions. Production validator and UUIDv7 allocator still needed. |
| Semantic v1 → reader artifact | **Proposed:** pure versioned compiler produces an output with explicit profile and revision binding; profile 1 JRT is usable only if actual parity is proven. Otherwise introduce profile 2 after the reader supports it. |
| Semantic v1 → Markdown/directives → semantic v1 | **Untested future option:** require canonical semantic round-trips before enabling edits through this source. Until then, export is read-only. |
| Opaque legacy block → editor/read/export | **Proposed:** preserve exact bytes/payload and show a placeholder or legacy reader fragment; disallow edits that would lose it. The synthetic placeholder alone is not an importer. |

| Transition | Authority while editing | Derived state / failure behavior |
| --- | --- | --- |
| Open legacy revision | Exact Pug source plus its selected JRT artifact are immutable authority for that revision | Legacy source editor may create a new v2 save; WYSIWYG conversion starts only after parity review. |
| Open semantic revision | Saved semantic v1 revision | Hydrate editor JSON, reader artifact and local draft; if adapter fails, retain saved content and offer source/recovery view. |
| WYSIWYG edit | In-memory semantic draft after validated editor → semantic conversion | Editor state is a view; compiled preview is disposable and must not be saved from a stale render. |
| Source-mode edit / mode switch | Source buffer is draft authority until successfully parsed and validated | Failed parse or conversion stays in source mode and leaves last valid semantic document unchanged. Successful apply replaces semantic draft and rehydrates editor. |
| Save | Exact validated submitted representation of this **new** revision | Server compiles that exact submission, stores source/semantic revision and artifact atomically, updates selected pointers with CAS, records idempotent receipt. Retry same immutable operation ID/payload. |
| Reload | Committed revision selected by the parent | Recover local unsent draft separately; compare base revision/version before offering replay. Never silently overwrite a newer server revision. |
| Conflict | Server's committed revision remains authoritative; local draft remains recoverable | Fetch current, show a comparison/explicit reapply path, allocate a new operation ID only for a consciously new submission. No automatic multi-author merge. |

For a semantic save, the existing source column cannot be relabeled Pug while storing JSON. A future **v3 write protocol/schema proposal** should add a semantic format/version and exact canonical submitted payload bytes/hash (or a dedicated immutable semantic column), compiler identity, output format/profile, and an artifact bound to that revision in one transaction. Extend the current v2 CAS on both revision and parent version, permission checks and immutable idempotency receipt; keep UUIDv7 operation IDs and actor precondition. Persist the original author submission exactly as accepted for a source-mode save and define a deterministic canonical encoding for WYSIWYG submissions. A retry must replay the same bytes and receipt. Do not create a second editable source copy that can drift from the semantic authority. Offline drafts stay local and tagged with base revision/version; reconnect sends the same immutable request until acknowledged or explicitly reconciled. The exact SQL shape and compatibility rollout require separate approval and review.

**Rollout order:** (1) land a pure semantic schema/validator/adapter and synthetic plus representative sanitized legacy parity tests; (2) add a read-only renderer and support the new output profile before any writer selects it; (3) provide opt-in import preview and fallback for unsupported revisions; (4) add versioned writer/receipt changes and offline draft migration behind a flag; (5) pilot editor with real authors and devices, then widen by ritual/role. Old readers must either continue to receive selected profile-1 artifacts with proven parity or receive an explicit update-required response before semantic writes become visible; they must not silently render a wrong profile. Existing cached private rituals, images and fonts remain readable offline throughout. Realtime collaboration and CRDTs are out of scope.

## Acceptance gates, risks and rollback limits

1. **Semantic parity gate:** sanitized representative rituals, including all production block variants, compile and round-trip without lost tasks, role scope, variables, nested content, links, assets or source-only data. Unknown nodes are visible and recoverable. The fixture is insufficient by itself.
2. **Authoring gate:** task boundaries remain safe through typing, selection, paste, drag/drop, undo/redo, split/merge and source mode. Test keyboard and screen readers, physical iOS/Android IMEs (including Hebrew and another composing keyboard), and a nontechnical participant doing realistic tasks. Confirm accessible task labels/controls and focus order. These are **untested** now.
3. **Contract gate:** reader output parity, exact revision/artifact binding, compiler identity/profile compatibility, CAS conflicts, duplicate delivery, lost acknowledgement, invalid source and offline drafts pass automated and browser tests. Review any v3 schema/protocol migration separately.
4. **Performance gate:** measure production Next editor and read-only route chunks, long real rituals, input responsiveness and offline cold opens on target devices. Vite numbers are a sizing clue only.
5. **Release gate:** activate new readers before semantic writers; preserve old source/artifacts; rehearse rollback and offline clients. Before the first semantic write, disabling the flag is simple. After semantic revisions exist, rollback requires a reader and recovery path that understands them; reverting only the UI would strand new work. Do not destructively rewrite old revisions.

The decision changes if Tiptap cannot maintain role-boundary semantics in the fuller schema, cannot meet physical-device/accessibility gates, imposes unacceptable Next bundle/interaction cost, or requires paid features for a necessary editor action. In that case, compare a guarded Lexical implementation and a Slate boundary plugin against the same fixture and gates; do not assume the focused Lexical failure is inherent to the engine.

An app-local reusable core could contain `SemanticDocument` types/validation, identity and conversion utilities, a pure read-only renderer and versioned compiler interface. Magickli owns roles, officer rules, grade glyphs, variable definitions, access policy, ritual assets and write protocol. Majou could later reuse the generic core after its own document use case proves which abstractions are shared. No Loom packaging is proposed at this stage.
